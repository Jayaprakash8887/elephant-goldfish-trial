# API integration

The console talks to one backend, `cce-admin-service`, under `/admin/v1`. All request and
response types are in [`src/api/contract.ts`](../src/api/contract.ts), which is a hand-written
mirror of the service contract
([`docs/designs/cce-admin-service.md`](../../docs/designs/cce-admin-service.md) §4). The service
code is in [`../../cce-admin-service/src/main/java/org/cce/admin/controller/`](../../cce-admin-service/src/main/java/org/cce/admin/controller/).

## How a request is made

- URL: `${VITE_API_BASE_URL}/admin/v1{path}`. `VITE_API_BASE_URL` is empty by default, so the
  request goes to the console's own origin. Locally the Vite proxy forwards `/admin/v1` to
  `http://localhost:8085`. In a deployment, Caddy forwards it to `gateway-service`.
- Headers: `Authorization: Bearer <access token>`, `Accept: application/json`, and
  `Content-Type: application/json` when there is a body.
- Success envelope: `{ data, pagination?, warnings? }`. Error envelope:
  `{ error: { code, message, details?, partialState? } }`.
- Errors are thrown as `ApiError`. For the 401 refresh-and-repeat flow, see
  [architecture-overview.md](architecture-overview.md#401-handling-in-the-client).

Notes:

- **Deactivate / Activate a menu** (`useToggleMenuActive` in
  [useMenus.ts](../src/hooks/useMenus.ts)) first reads `GET /menus` again. It takes the entry's
  current `label`, `path`, `icon`, `parentId` and `sortOrder`, then sends `PUT /menus/:id` with
  `isActive` flipped. If the entry is no longer in the tree, it sends no PUT and throws a
  client-made `ApiError` 404 `MENU_NOT_FOUND` with "This menu no longer exists."
- **`useAllRoles`** reads at most five pages of 100 roles, joins them and drops duplicate ids.
  `truncated` is `true` when `totalPages > 5`. The pickers then say "Showing the first 500
  roles." Pickers and the role filter show only roles with `isAssignable: true`.
- The value returned by `POST /roles/:id/sync` is not used directly. The refetch rule reloads the
  permissions and the role, and the badges show the status the service now reports.
- After every successful mutation, the query client refetches every active query (see
  [architecture-overview.md](architecture-overview.md#query-layer)).

## Warnings in success responses

| Code                    | Endpoint               | What the console does                                                                                                                                                                                                                                                                      |
| ----------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ACTION_EMAIL_NOT_SENT` | `POST /users`          | User edit shows a `WarningList`: "User created, but the set-password email could not be sent. Use Send set-password email on this page." in place of the success notice.                                                                                                                   |
| `ROLE_SYNC_FAILED`      | `POST /roles`          | Navigates to `/roles/{id}?tab=permissions` with state `createdWithSyncWarning`. The tab shows "The role was created but not synced. Use Re-sync before assigning it."                                                                                                                      |
| `DETAIL_WITHOUT_PARENT` | `PUT /roles/:id/menus` | The Menus tab replaces its own client-side warnings with the server's. Each one is shown as "{detail label} is shown only when {parent label} is also granted.", with labels looked up by `menuId` and `parentMenuId`. If an id is not in the tree, the server `message` is shown instead. |

Other warnings in a response are ignored.

## Error handling by kind

[`describeError`](../src/utils/describeError.ts) turns every error into a kind. The kinds table
is in [architecture-overview.md](architecture-overview.md#error-presentation). Two general rules:

- **Failed query**: an `InlineError` with a Retry button that refetches. Queries retry once by
  themselves for status 0 and 5xx.
- **Failed mutation**: the error appears next to the action. For `network` and `unexpected`, it
  adds "The result is unknown; the page was refreshed." and the refetch rule runs. After a 4xx
  with the service's envelope, nothing is refetched.

## Sync failures (502 `KEYCLOAK_SYNC_FAILED`)

[`SyncFailedNotice`](../src/components/shared/SyncFailedNotice.tsx) is an amber `role="alert"`
box. It shows:

1. The server `message`.
2. A next-step text. "The service recorded no change. You can try again." when
   `completedSteps` is empty. Otherwise the operation's text below. `ROLE_SYNC` always shows its
   own text.
3. "For the operator:" with "Keycloak user id: …" and "Audit log id: …", when either is not
   null.
4. Optional actions: Re-sync, or a "Back to users" link.

A 502 is in the refetch rule, so the page data reloads. The form or button that sent the request
keeps the administrator's input, so the same request can be sent again.

| `partialState.operation` | Shown where                                             | Text when steps completed                                                                                                                                                                                      | Actions and behaviour                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `USER_CREATE`            | User create, above the form                             | "The sign-in account may exist in Keycloak without a user here. Submit the form again with the same values: the service links the account and finishes. If it fails again, pass the ids below to an operator." | "Back to users" link. The form keeps its values and its "Create user" button.                                                                                                  |
| `USER_PROFILE_UPDATE`    | User edit, Profile section                              | "Keycloak may have the new values while this page shows the old ones. Save the profile again with the same values. …"                                                                                          | The form keeps the values sent.                                                                                                                                                |
| `USER_STATUS_CHANGE`     | User edit, Status section; Users list row result area   | "Keycloak may already have the new status, but it was not saved here. Choose the same status again. …"                                                                                                         | none                                                                                                                                                                           |
| `USER_ROLES_UPDATE`      | User edit, Roles section (next to Save roles)           | "Some Keycloak role mappings may have changed, but the roles were not saved here. Save the same roles again. …"                                                                                                | The selection sent is kept.                                                                                                                                                    |
| `USER_PASSWORD_RESET`    | User edit, Password section; Users list row result area | none; its steps are always empty, so the "no change" text applies                                                                                                                                              | none                                                                                                                                                                           |
| `ROLE_PERMISSIONS_SAVE`  | Role detail, Permissions tab                            | "The permissions were saved but not synced. Use Re-sync, and do not assign the role until a sync succeeds."                                                                                                    | Re-sync button. The rows were saved, so the tab refetches the permissions and remounts the editor with them. Save becomes disabled and the badge shows "Sync failed · {time}". |
| `ROLE_SYNC`              | Role detail, Permissions tab (after Re-sync)            | always "The sync failed. The saved permissions are unchanged. Use Re-sync."                                                                                                                                    | Re-sync button. Unsaved edits in the editor are kept.                                                                                                                          |

A 502 that is not the service's envelope (a gateway or proxy error page) is not a sync failure.
It shows as `unexpected` (see the table above).

The sync status shown in badges is always the server's (`Role.syncStatus` and
`RolePermissions.syncStatus`: `NEVER`, `SYNCED`, `FAILED`). The console never sets it.

## Service endpoints the console does not call

| Endpoint                                     | Note                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `GET /admin/v1/me/menus`                     | Returns the caller's granted menu tree. The console's sidebar is static, so it does not use it.  |
| `DELETE /admin/v1/menus/:id`                 | No menu delete in the UI. Menus are deactivated instead.                                         |
| `GET /admin/v1/health`                       | Not called by the app. The Playwright global setup calls it directly on `http://localhost:8085`. |
| `/admin/v1/api-docs`, `/admin/v1/swagger-ui` | springdoc OpenAPI docs of the service. Not used.                                                 |

The browser tests also call some endpoints directly, outside the console, to create test data
(`POST /roles`, `PUT /roles/:id/permissions`, `POST /users`, `GET /users/:id`, `GET /roles`). See
[`e2e/fixtures.ts`](../e2e/fixtures.ts).

## Keeping the contract in sync

`contract.ts` and [`src/schemas/rules.ts`](../src/schemas/rules.ts) (patterns and length limits)
are copied by hand from the service design. No test checks them against the running service. The
MSW handlers in [`src/test/mocks/handlers.ts`](../src/test/mocks/handlers.ts) are typed from
`contract.ts`, so they cannot detect drift either. Only the Playwright tests run against the
real service. When the service contract changes, update `contract.ts`, `rules.ts`, the fixtures
and the handlers together.
